## 1. 结论

**单路非流式对话通过；把并发拉到准入上限 200 时，本机扛不住。**

200 是 `box.chat-admission.max-inflight` 的默认值，也接近 Tomcat 默认工作线程。非流式 `sendMessage` 在 **同一事务里等模型**，会长时间占着 Tomcat 线程和 Hikari 连接（默认池约 10）。200 路同时打时，多数请求在门外排队，最后失败，不是登录那种开闸 `connection refused`。

| | 1 VU × 20s | **200 VU × 2 分钟** |
|---|---|---|
| 发消息 | 6 / 6 | **57 成功 / 656 失败** |
| HTTP 失败率 | 0% | **91.9%** |
| checks | 100% | 8.1% |
| p95 | 4.6s | **62s**（阈值 30s，未过） |
| 库里成功 execution | — | 64 条，平均 **2.5s**（最快 0.9s，最慢 11s） |
| k6 退出 | 0 | 99 |
| 结束后 health | — | 仍 `UP` |

成功打到模型的请求本身很快；k6 看到的几十秒是排队，不是单次推理。失败请求没有留下 `execution` 失败行（`@Transactional` 回滚）。结束时仍有 68 个 VU 在 graceful stop 里被打断。

## 3. 数字怎么读

- 建连是成功的（`http_req_connecting` 最大 38ms），**不是** 登录/注册那种第 0 秒拒连。
- 阈值 `http_req_failed < 5%`、`checks > 90%`、`p(95) < 30s` 全部未过。
- 吞吐约 **4.8 req/s**，接近「连接池能同时做的对话数 × 单次 2～3s」，而不是 200 路并行。

---

## 4. 建议

- 本机 **不要** 把「200 路非流式同时成功」当成现网能力。准入 200 是全局在途上限，非流式还会被线程池和数据库连接池先卡住。
- 生产仍有 60 次/用户/分钟；单个用户打不出 200 路。多用户合计接近 200 路**同步**对话时，需要把 LLM 调出事务、加大连接池，或主要靠 SSE（虚拟线程，不长时间占 Tomcat 工作线程）。
- SSE 同规模已跑，见 [2026-11-06-chat-sse-200vu.md](./2026-11-06-chat-sse-200vu.md)（阈值通过）。
- RAG、开放 API 已跑，见 [SUMMARY.md](./SUMMARY.md)。
