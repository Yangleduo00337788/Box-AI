## 1. 结论

**k6 预设阈值全部通过**（失败率 < 1%、检查通过率 > 99%、p95 < 800ms），但属于贴线通过，不能当成上线容量结论。

- 1000 个 VU **同时拉起**时，本机 Tomcat 出现一批 `connection refused`（目标机器主动拒绝连接）。
- 随后服务恢复，整体失败率 **0.75%**，p95 **283ms**（对比同机 50 VU 的 p95 **6.3ms**，延迟抬升约 45 倍）。
- 压测结束后 `/api/v1/system/health` 仍为 `UP`（MySQL / Redis 正常）。
- 本次只压 **控制台读接口**，未压 Chat / RAG / 已发布 Agent（不消耗模型）。

**建议**：上线环境不要用「瞬间 1000 VU」当验收；应斜坡加压，并单独评估对话链路。本机默认线程池与连接队列不足以作为生产容量依据。

## 6. 现象与原因

1. **瞬时连接风暴**  
   1000 VU 在 0s 同时建连，超过 Windows / Tomcat 默认 accept 队列，出现 `connection refused`。斜坡加压（`PROFILE=heavy`：20s 拉到 1000）可减轻这类误伤。

2. **延迟从毫秒级进入百毫秒**  
   50 VU 时 p95 6ms，说明单机读路径很轻；1000 VU 时平均 152ms、p95 283ms，已进入线程排队 / 连接等待区间（Tomcat 默认 `maxThreads` 约 200）。

3. **进程未崩溃**  
   压测结束后健康检查仍 UP，属于过载降质而不是宕机。

4. **业务限流未触发为主因**  
   登录只在 setup 打了 1 次（登录限流 20 次/IP/分钟，此处无关）。Chat 限流未参与。

## 8. 后续建议

1. 上线验收用斜坡：`.\run.ps1 -Scenario mixed -Profile heavy`，或先 200 → 500 → 1000，避免把「拒连」算进容量。
2. 若生产要扛接近千级并发读：调 Tomcat 线程与 accept-count、操作系统连接 backlog，并在网关做连接与 QPS 限制。
3. 对话上线必须另跑 `chat` / `published`，VU 按模型配额设（控制台 Chat 60 次/用户/分钟，API Key 120 次/分钟）。
4. 在预发（接近生产配置）复测后再写容量数字；本机 `dev` 结果只说明「读接口在过载下仍能工作」，不能写成 SLA。
