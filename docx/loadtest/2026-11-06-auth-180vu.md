## 1. 结论

**登录业务正确性通过，容量阈值未过。** 180 VU × 1 分钟下，成功登录后的 `GET /auth/me` **100%**；失败全部是开闸瞬间 TCP `connection refused`，没有 `code != 0`、没有 429、没有死锁。

k6 登录类阈值：p95 < 1.5s **通过**（1.08s）；失败率 < 5%、checks > 95% **未过**（失败 6.25%、checks 93.74%）。k6 退出码 99。

压测结束后 `/api/v1/system/health` 仍为 `UP`（MySQL / Redis 正常）。本轮 **关了接口限流**，测的是 bcrypt + 发 JWT 的容量，不是生产默认「20 次/IP/分钟」。

未压 Chat / RAG / 已发布 Agent。

## 3. 场景

脚本每轮：`POST /api/v1/auth/login` → `GET /api/v1/auth/me`，再 `sleep(1)`。登录失败会抛错，**不会 sleep**，VU 立刻下一轮，因此开闸拒连会被放大。

阈值：`http_req_failed < 5%`、`checks > 95%`、`p(95) < 1500ms`。

| | smoke 16:51 | 180 VU 16:51 |
|---|---|---|
| 规模 | 2 VU × 30s | **180 VU × 1 分钟** |
| 迭代 | 56 | 6,672 |
| HTTP 请求 | 112 | 12,559 |
| 吞吐 | 1.8 iter/s | **107 iter/s** |
| 登录 | 56 / 56 | **5,887 成功 / 785 失败** |
| `/auth/me` | 56 / 56 | **5,887 / 5,887** |
| HTTP 失败率 | **0%** | **6.25%** |
| checks | **100%** | 93.74% |
| p95 | 79ms | **1.08s**（阈值通过） |
| p99 | 86ms | 1.23s |
| 最大 | 87ms | 2.13s |
| k6 退出 | 0 | 99（失败率 + checks） |

785 次失败全部是 `dial tcp 127.0.0.1:8080: connectex: No connection could be made because the target machine actively refused it`，与 11-04 mixed、11-06 register 开闸现象同类。比注册那轮（11 次拒连）多，是因为登录失败不 sleep、180 个 VU 在第 0 秒同时 `POST /login`。

## 4. 和建议

- 小流量登录无压力（2 VU 时 p95 79ms）。
- 瞬间 180 VU 会打满本机 Tomcat accept 队列；连上之后登录本身能完成，p95 约 1s，主要是 bcrypt。
- 不要把本轮失败率当成「登录接口 6% 业务错误」。生产默认还会再套一层 20 次/IP/分钟，真实用户打不到这个并发。
- 若要验收限流：把 `BOX_RATE_LIMIT_ENABLED=true` 后用 2～5 VU 跑同一脚本，预期大量 429，而不是 200。
- 对话见 [chat-sse 200 VU](./2026-11-06-chat-sse-200vu.md)；开放 API 见 [published 200 VU](./2026-11-06-published-200vu.md)。
